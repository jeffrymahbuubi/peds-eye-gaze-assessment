## 1. Control Address / localhost confusion — resolved, not a bug

**Reported:** using `127.0.0.1` as Control Address still connects to the device and still opens the real Gazepoint Control calibration window — user expected localhost to fail since "the device is not local."

**Root cause:** not a bug. Gazepoint Control (the vendor app) always runs on the same PC the Python client connects to — the GP3 HD talks to Gazepoint Control over USB, never over the network, and Gazepoint Control draws the calibration window on whatever monitor is attached to that same PC. `src/inputs/gazepoint_client.py`'s module docstring documents the default endpoint as `127.0.0.1:4242`. `configs/default.yaml`'s current `gazepoint.host: "26.113.49.235"` is leftover from this specific dev machine's own Radmin VPN adapter address (confirmed via `netstat`/`ipconfig` in a prior session, see the `peds-eye-gaze-assessment-calibration-crash-2026-09-09` memory) — not a second physical machine, and not something any future deployment needs to replicate.

**Confirmed by the user (2026-09-10):** `127.0.0.1` always works, on any computer, because the Python client and Gazepoint Control are always the same machine by this project's design — no IP ever needs to be copied out of Gazepoint Control's own UI.

**Status: IMPLEMENTED and live-validated against the real device (2026-09-10).** See the Log below for the full account.

## 2a. Calibration per-point breakdown intermittently "not available" — race condition

**Reported:** "View Calibration Details" sometimes shows "per-point breakdown not available for this calibration"; redoing the calibration doesn't reliably fix it.

**Root cause:** `Calibration._poll_for_result()` (`src/engine/calibration.py:335-391`) does two independent things at once: it actively polls `CALIBRATE_RESULT_SUMMARY` every 0.5s (`_POLL_INTERVAL_S`), and it separately, opportunistically, captures the unsolicited `CALIB_RESULT` push (per-point/per-eye data, parsed by `_parse_calib_result`, lines 33-66). Per the vendor manual (`docs/gazepoints/sources/gazepoint-api.md` §4.3, ~line 604-606), `CALIB_RESULT` is pushed only once, at the very end of the entire calibration process, after every point's animation finishes. But `_poll_for_result` returns immediately (line 382-383) the instant a `CALIBRATE_RESULT_SUMMARY` ACK shows `VALID_POINTS >= n_points`, with no wait to see whether `CALIB_RESULT` is still in flight. Whether the summary ACK or the `CALIB_RESULT` push wins the race is timing-dependent (order across `recv()` chunks), which matches the reported "sometimes works, sometimes doesn't, redoing it doesn't help" symptom exactly — it's a coin-flip, not a hardware or data problem.

**Status: IMPLEMENTED and tested (2026-09-10).** See the Log below for the full account.

## 2b. Calibration-file / session-folder reorganization

**Reported/proposed:** user wants an explicit "Save Calibration" action (decoupled from "Do Calibration") and a folder layout of `Subject ID/calibration.json` + `run_1/`, `run_2/`, ... `run_n/`, so a calibration can be replaced later if seating/camera position changes between sessions.

**Current state:** `calibration.json` auto-saves (no separate save action) into each individual run's own folder (`sessions/<date>_<subject>_<task>_run<N>/calibration.json`) only when a real, freshly-measured calibration executes — not on a reused/loaded one (`src/app.py:198-223`). "Load Calibration File" already lets the operator browse to **any** `calibration.json` via a file picker (not restricted to one folder) and hard-errors on a subject-ID mismatch (`CalibrationFileError`, `src/engine/calibration.py:115-176`) — so the cross-session reuse *mechanism* already exists. What's actually missing is (a) a user-visible "save/promote this calibration" action independent of running a fresh calibration, and (b) one canonical per-subject location to look in, instead of hunting through dated run folders.

**Two options evaluated:**
- **Recommended (smaller, lower-risk):** add a "Save Calibration" button that copies the current calibration to a fixed `sessions/_calibrations/<subject_id>/calibration.json`, and default "Load Calibration File"'s file picker to open there first. No change to the existing per-run folder layout; touches only `setup_page.py` and a small helper.
- **Alternative (the user's original proposal, higher risk):** restructure to `Subject ID/calibration.json` + `run_1..run_n/` — would touch `session_naming.py`, `app.py`'s session-dir computation, and the file-picker default path. Rejected for now in favor of the smaller option, but documented here in case the user prefers it after seeing the tradeoff.

**Status: IMPLEMENTED and live-validated (2026-09-10)**, the recommended smaller option. See the Log below for the full account.

## 4. Smoothing alpha / jitter tolerance / refractory period — explanation only

**Reported:** user wasn't sure which parameter controls gaze-cursor smoothness, and didn't know what `jitter_tolerance_px`/`refractory_ms` mean; guessed lowering smoothing alpha would reduce jitter.

These are three unrelated knobs (`configs/default.yaml`'s `dwell` block, logic in `src/inputs/eye_input.py`):

- **`dwell.smoothing.alpha`** (0.05-1.0, currently 0.35) — the only one that actually controls visual cursor jitter. It's an exponential moving average applied to the pointer before it's drawn or hit-tested (`GazeSmoother.update`, `eye_input.py:71-78`). Lower = smoother but laggier; higher = snappier but jitterier. The user's instinct to lower it is correct.
- **`dwell.jitter_tolerance_px`** (0-100px, currently 40) — spatial hitbox padding for "is gaze on-target", not cursor smoothness (`settings_registry.py:108-118`). Raising it makes selection more forgiving of small position error; does nothing to how the cursor looks.
- **`dwell.refractory_ms`** (0-2000ms, currently 500) — a post-selection cooldown preventing the same dwell from re-triggering immediately (`DwellSelector`, `eye_input.py:88-144`); unrelated to jitter or targeting.

**Recommendation:** try `smoothing.alpha` in the 0.20-0.25 range for a visibly smoother cursor without excessive lag (current 0.35 is mid-range); leave `jitter_tolerance_px`/`refractory_ms` alone unless a *targeting* (not smoothness) problem shows up.

**Status: APPLIED (2026-09-10, round 3).** Tested live during a real task run with a real subject: alpha was changed from `0.35` to `0.22` through the operator panel's own live control while the cursor was visible, and the user judged 0.22 better. `configs/default.yaml`'s `dwell.smoothing.alpha` is now `0.22`. Note that file is skip-worktree'd on this machine, so the new default is real and in effect locally but is **not** part of any commit — same as the `gazepoint.host` value (item 1).

## 5. Right-side targeting difficulty — likely root cause found, not yet proven live

**Reported:** targets/icons on the right side of the task screen are hard for the child's gaze to reach, across all tasks.

**Root cause (code-grounded, highest-value finding this session):** Gazepoint's `BPOGX`/`BPOGY` are normalized (0-1) against the OpenGaze `SCREEN_SIZE` setting — the full physical monitor Gazepoint Control is tracking (`docs/gazepoints/synthesis/api-reference.md:90`), entirely independent of this app's window. But this app's hit-testing normalizes gaze against `self.canvas.width()`/`height()` — the canvas widget's own size (`src/app.py:419`, `BaseTask.set_screen_size`, `src/tasks/base_task.py:107-122`) — which is **never** equal to the full tracked monitor:

- `configs/default.yaml:6` currently has `app.fullscreen: false`, so the standalone window is windowed at 1280×800 (`src/ui/main_window.py:66`), not fullscreen.
- Even when `fullscreen: true`, the canvas sits next to a **fixed 280px-wide OperatorPanel sidebar** (`src/ui/main_window.py:39-43`), so canvas width is always `monitor_width − 280`, never the full monitor.
- The dashboard flow (the actual path physicians use today) opens at a fixed **1024×800** (`src/ui/dashboard_window.py:94`) regardless of the real monitor's size.

**Effect:** a target drawn at canvas-normalized x=0.85 sits at a real on-screen pixel position that is *less than* 85% across the actual monitor. The tracker reports that real position back as a `BPOGX` value lower than 0.85 (since it's normalized against the full monitor). Hit-testing then re-multiplies that lower value by the canvas width again, placing the computed cursor short of the drawn target — the child must look further right than the target's real position to register a hit. The error grows with distance from center and is worst toward whichever edge is furthest from the canvas's actual on-screen position — this reproduces "hard to reach the right side" without needing any hardware/tracking-quality explanation.

This is distinct from the already-fixed Aug-31 hit-testing bug (`peds-eye-gaze-assessment-hittesting-fix-2026-08-31` memory), which only addressed canvas-size-vs-*config-default* mismatch (1920×1080 default vs. live canvas size) — never canvas-vs-*full-monitor* mismatch, which only shows up once there's a sidebar or a non-fullscreen window (both true today).

**Recommended fix:** convert gaze to pixels using real monitor/screen geometry (Gazepoint's own `SCREEN_SIZE` via `GET`, or Qt's `QScreen.geometry()`) plus the canvas's actual on-screen offset — not the canvas widget's local width/height.

**Status: IMPLEMENTED, unit-tested, and live-validated (2026-09-10).** See the Log below for the full account.

## 6. Gaze cursor rendering never received item 5's coordinate fix — confirmed root cause, not yet implemented

**Reported (round 2):** the visible gaze cursor sometimes disappears mid-task even though the subject isn't blinking; gazing at a circle other than the center one makes it vanish. Reference screenshots at `resources/images/gaze-cursor-from-calib/` show Gazepoint Control's own calibration-result overlay, where the gaze marker is drawn wherever real gaze lands (including well outside any calibration target, e.g. one screenshot shows it near a corner and another shows it isolated below the grid) and is **never clipped or hidden** — the user wants the app's own cursor to behave the same way, always present.

**Root cause, confirmed directly from source (no live test needed to establish this structurally):** item 5's fix only reaches hit-testing, never the drawn cursor.

- `src/app.py:458` feeds the canvas the **raw** pointer: `cursor_xy_norm=(pointer.x, pointer.y)`. `pointer.x/y` are `GazepointClient`'s `BPOGX`/`BPOGY`-derived values, normalized against the **tracked monitor** (confirmed at `src/inputs/gazepoint_client.py`'s own `SCREEN_SIZE` docstring, lines ~119-121 — "what `BPOGX`/`BPOGY` are actually normalized against, independent of this app's own window").
- `src/ui/canvas.py`'s `TaskCanvas._draw_cursor` (called from `paintEvent`, line 131) converts that value via `norm_to_px(*self.cursor_xy_norm, w, h)` where `w, h = self.width(), self.height()` — the **canvas widget's own current pixel size**. No offset, no tracked-screen dimensions, no reference to `_gaze_geometry` anywhere in `canvas.py`.
- By contrast, `src/tasks/base_task.py::BaseTask.update()` (lines 220-227) computes a **second, separate** pixel position (`px, py`) for hit-testing only, which *does* apply `set_gaze_geometry`'s corrected conversion (tracked-screen size + canvas offset) when available. This second, corrected value is never sent anywhere the canvas can draw it.

**Net effect:** the cursor drawn on screen and the point the engine actually tests against for hits are computed by two different formulas. Item 5 already established, via its own live measurement this same day, that the real canvas is smaller than the real window (`744×845` inside `1024×897`) — meaning real gaze that is monitor-normalized and then reinterpreted as canvas-normalized will, for any gaze position past roughly canvas-width/monitor-width of the way across, compute a pixel position **outside the canvas widget's rect**. Qt clips `paintEvent` drawing to the widget's own bounds, so the cursor silently disappears rather than erroring — worse the further the real gaze is from the canvas's own on-screen center, which matches "gaze at another circle → cursor vanishes" exactly. This also explains why the item-5 audit still looked broken to the user: item 5 never touched what's rendered, so nothing about the visible cursor's behavior could have changed from that fix.

**Not yet live-validated against the real device this round** (diagnosis is from source + item 5's own already-recorded live measurements; no cooperative subject available this session, matching this project's disruptive-live-launch caution — see `feedback-check-disruptive-paths-before-live-launch` memory).

**Decided fix direction (via `AskUserQuestion`): fix the mapping AND clamp to the canvas edge.** Two parts:

1. **Mapping fix:** have `src/app.py` compute the cursor's position the same way `BaseTask.update()` already does for hit-testing (tracked-screen size + canvas offset via `_gaze_geometry`), rather than passing raw `pointer.x/y` straight to the canvas. This requires exposing the corrected canvas-local pixel (or an equivalent canvas-normalized fraction) from `BaseTask`/the app tick loop to `TaskCanvas.set_frame`, not just using it internally for `on_target`.
2. **Edge clamp:** when the corrected position falls outside the canvas's own `[0,1]` normalized range (i.e., real gaze is off the canvas entirely — e.g. on the `OperatorPanel` sidebar), clamp the drawn cursor to the nearest canvas edge instead of not drawing it, so a dot is always visible somewhere on the canvas, closest to Gazepoint Control's own always-present behavior. This is a deliberate trade-off the user accepted: it means "gaze left the canvas entirely" is no longer visually distinguishable from "gaze is at the very edge of the canvas" — flagged here in case that distinction ever matters clinically later.

**Open implementation questions for the next session** (not resolved this round, since this round is diagnosis-only): whether the clamp is a simple per-axis `min`/`max` to `[0,1]` before `norm_to_px`, and whether `cursor_valid`'s existing dim-alpha treatment (already in `_draw_cursor`, `70` vs `200` alpha) should also apply while clamped, so a clamped-at-edge cursor still visually reads as "at the boundary," not fully valid on-target.

**Status: IMPLEMENTED and live-validated with a real subject (2026-09-10, round 3).** See the Log below for the full account. Both open implementation questions were resolved: the clamp is a per-axis `min`/`max` in *pixel* space (inset by the cursor's own radius, so a clamped dot is drawn whole rather than half-cut by the widget boundary), and a clamped cursor does reuse the existing dim-alpha treatment, so "gaze at the canvas edge" stays visually distinguishable from "gaze left the canvas" — recovering most of the trade-off this section had accepted losing.

## 7. Calibration per-point breakdown still unavailable at n=4/n=5 despite item 2a's grace window — needs live timing data

**Reported (round 2):** with `calibration.points` set to 4 or 5, "View Calibration Details" sometimes still shows the "not available" placeholder even after waiting several seconds before clicking; with 6 or more points it reportedly always works.

**Confirmed from source: waiting in the UI cannot help, regardless of point count.** `src/ui/setup_page.py::_populate_calibration_details()` (line 781) only ever reads whatever `self._calibration_result.per_point` already contains — a value that was fixed the moment `Calibration.run()` returned, back when "Do Calibration" was clicked. There is no re-query, no background retry, and no code path that fills in `per_point` after the fact. So item 2a's fix (`_CALIB_RESULT_GRACE_S = 0.75`, `src/engine/calibration.py:234`) is the *entire* window in which the per-point breakdown can still be captured — if `CALIB_RESULT` hasn't arrived within 0.75s of `CALIBRATE_RESULT_SUMMARY` reporting every point valid, `_poll_for_result` gives up and returns `per_point=None` for good (lines 372-373, 422-427). This matches the reported symptom exactly: it isn't that the *button* sometimes fails, it's that the capture opportunity already permanently closed a few seconds earlier, inside a call the Setup page already finished waiting on before the alert ever said "Calibration measured."

**Why n=4/5 would lose this fixed-0.75s race more often than n≥6 — a hypothesis, not yet proven:** nothing in `_poll_for_result`, `_configure_points`, or the timeout math (`_timeout_s`, lines 279-289) treats point count differently in a way that would explain this from source alone — the grace window is a flat constant regardless of `n_points`, and the *overall* poll deadline actually scales *up* with more points (more points ⇒ more allowed time, not less), which runs the opposite direction from a "more points is more reliable" explanation if the mechanism were simply "more time available." The leading hypothesis, informed by this project's own prior finding that the real GP3 HD enforces a hard minimum of 4 valid points to compute a calibration at all (`peds-eye-gaze-assessment-physician-feedback-2026-09-02` memory: "insufficient valid points... minimum required is 4"): calibrating close to that floor (n=4, and to a lesser extent n=5) may leave the device's own internal regression more marginal/sensitive to any single imperfect point, which could plausibly make its post-summary `CALIB_RESULT` computation-and-send slower or less deterministic than when there's headroom above the floor (n≥6) — but this is unverified. It is equally possible the real explanation is unrelated to point count at all (e.g. general network/scheduling jitter that just happened to correlate with point count across a small number of manual trials).

**Decided next step (via `AskUserQuestion`): add a live timing diagnostic before choosing a fix**, rather than guessing at a new grace-window value. Proposed for the next implementation session (not done this round): temporarily log, on every real `Do Calibration` run, the wall-clock gap between the `CALIBRATE_RESULT_SUMMARY` ACK that first reports full validity and the `CALIB_RESULT` push (or "never arrived, timed out" if it doesn't), across a handful of real-device runs at n=4, n=5, and n≥6 each. That data either confirms the near-floor hypothesis above (gap scales with proximity to n=4) or points somewhere else (e.g. a gap that's roughly constant regardless of n, meaning 0.75s is just occasionally too tight everywhere and 4/5 simply drew the short straw in a small sample) — either result tells us what to actually change (a larger/adaptive grace window, a different capture strategy, or nothing beyond expectation-setting if it turns out to be rare/random).

**Status: ANSWERED by the live diagnostic (2026-09-10, round 3) — and the answer was not what this section hypothesized.** The timing diagnostic was implemented and run against the real GP3 HD. Measured result:

```
t_summary_satisfied_s: 0.015    gap_s: 10.313    t_calib_result_s: 10.328
```

The gap between the satisfying `CALIBRATE_RESULT_SUMMARY` ACK and the `CALIB_RESULT` push is **10.3 seconds — the entire duration of the calibration**, not a sub-second race. `_CALIB_RESULT_GRACE_S = 0.75` was never remotely large enough, and **no value of that constant could have fixed this**, because the ACK being "satisfied" at 0.015s was never this calibration's ACK at all — it was Gazepoint Control's *retained previous* calibration, answered instantly (see §9).

**The n=4/5-near-the-4-point-floor hypothesis is therefore wrong, and is retracted.** Nothing about point count drives this. Per-point availability depended entirely on whether a stale prior result happened to be sitting in the socket or in Gazepoint Control's retained state — which correlates with how recently and how often the operator had calibrated, not with `calibration.points`. That also explains the reported "n≥6 always works" pattern as coincidence of usage, not a property of point count.

§7 is resolved by §9's fix rather than by a grace-window change: with the completion gate in place, `per_point` was captured on **every** post-fix run (see the Log). The grace window is retained for its original, genuinely-different purpose (a device that pushes `CALIB_RESULT` slightly *after* the real terminal ACK).

## 8. calibration.json naming should encode point count (new feature request)

**Reported (round 2):** the user has to open `calibration.json` to find out how many points a saved calibration used; wants the filename itself to show it.

**Current state, confirmed from source:** the filename `calibration.json` is hardcoded in three places — `src/app.py:206` and `:223` (per-run auto-save into the session directory) and `src/ui/setup_page.py:731`/`:746` (item 2b's per-subject canonical save/load at `_subject_calibration_dir(output_root, subject_id)/calibration.json`). `n_points` is already recorded inside the JSON payload itself (`CalibrationResult.n_points`, written by `save_calibration_result`) — this request is purely about the filename, not new data capture.

**Decided (via `AskUserQuestion`): one file per point-count, not one canonical file per subject.** `_subject_calibration_dir(...)/calibration.json` becomes `_subject_calibration_dir(...)/calibration_{n}pt.json` (e.g. `calibration_5pt.json`, `calibration_9pt.json`) — re-saving a calibration at a different point count no longer overwrites a previously-saved calibration at another point count for the same subject; both coexist. This changes item 2b's behavior, not just cosmetics:

- `_on_save_calibration_clicked()` needs to build the filename from `self._calibration_result.n_points` instead of the current fixed `"calibration.json"`.
- `_on_load_calibration_clicked()`'s default-path pre-selection (currently checks one fixed candidate path) needs to become "does *any* `calibration_*pt.json` exist for this subject" — and if more than one point-count has been saved for the same subject, needs a decision for which one to default to (most-recent by file mtime is the natural choice, matching how a single canonical file would have always reflected "the latest" before). **Not yet decided:** whether the file picker's default should be the most-recently-modified saved calibration across point counts, or whether Setup should surface all of a subject's saved calibrations (one per point count) as an explicit choice rather than silently picking one — left for the next implementation session.
- The per-run auto-save in `src/app.py` (`session_dir / "calibration.json"`) is a *different* mechanism (one per session folder, not per subject) and was not part of this request — left unchanged unless the user wants it renamed too.

**Status: IMPLEMENTED and live-validated (2026-09-10, round 3).** The open sub-question is resolved: "Load Calibration File" pre-selects the subject's **most recently modified** saved calibration across point counts (matching what a single canonical file always implicitly meant — "the latest"), while the picker still lists the others beside it, so overriding is one click. Pre-S8 `calibration.json` files are included in that search, so calibrations saved before this change are still offered. See the Log below.

## 9. Calibration reports the PREVIOUS run's result as if it were this one's — critical, found and fixed in round 3

**Found while running §7's diagnostic** (not reported by the user; the diagnostic's whole purpose was to produce data, and the data immediately showed something worse than the question it was built to answer).

**Symptom, measured against the real GP3 HD:** with Gazepoint Control's calibration window visibly animating its points on screen — confirmed by the user watching — `Calibration.run()` returned in **31–78 milliseconds**, reporting `valid: true` with a full per-point breakdown. A real 4- or 5-point calibration takes ~10.5s. The Setup page therefore announced "Calibration measured" while the child was still being calibrated, and the numbers it showed belonged to the *previous* calibration. Repeated `mean_error_px: 0.0` readings were also observed — the same "suspicious 0.0 calibration error" symptom recorded in the `peds-eye-gaze-assessment-calibration-config-2026-08-31` memory as previously fixed.

**Two independent causes, both confirmed and both fixed:**

1. **Leftover socket data from the previous calibration.** `_poll_for_result` queries `CALIBRATE_RESULT_SUMMARY` every `_POLL_INTERVAL_S` (0.5s) and returns on the first satisfying reply — so a ~10s calibration issues ~21 queries and consumes only one answer. The remaining replies (all reporting the just-finished calibration as fully valid), plus that run's `CALIB_RESULT` push, stay unread in the socket. The *next* calibration's poll drains them within milliseconds and treats them as its own. **Fix:** `_drain_socket()` discards anything already waiting before `CALIBRATE_START` is sent.

2. **Gazepoint Control's own retained result.** A socket drain cannot address this one: on a *fresh* connection, with nothing stale in the socket, the device still answered the very first result query at `t=0.031s` with the previous **app instance's** error value (13.46px). **Fix:** a completion gate — the unprompted `CALIB_RESULT` push (sent once, when this calibration actually ends, per API manual §4.3) is the only trustworthy evidence that a summary describes this run, so a satisfying summary is not accepted until either `CALIB_RESULT` has arrived or `_min_calibration_s` has elapsed.

**`_min_calibration_s` was tuned against the real device, not guessed.** A first attempt at `0.4 × n_points × per_point_s` (3.5s for n=5) was implemented and live-tested, and **still returned the retained result** — at 4.25s the device had nothing but its previous calibration to report. It is now `min(n_points × per_point_s × 1.25, timeout_s × 0.7)` — 10.7s for a default 5-point run, just under the ~10.3s at which the real `CALIB_RESULT` actually lands, and capped below the poll deadline so it can never swallow the whole timeout.

**Relationship to item 2a:** 2a's grace window is retained but is no longer what makes per-point capture work — the completion gate is. 2a was solving a real but much smaller problem (a `CALIB_RESULT` arriving slightly after the terminal ACK); it could not have solved this, because the ACK it was racing against was a stale one.

**Status: IMPLEMENTED, unit-tested with two reproduction-and-fix tests, and live-validated against the real GP3 HD.** See the Log below.
