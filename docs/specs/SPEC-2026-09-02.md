## Context

The user (PI's collaborator) met with a physician who tested the assessment tool with `follow_along` and the other three tasks. This raised several questions and one usability complaint about jitter. Goal of this session: understand and diagnose each item, not fix it.

## 1. Visual cursor jitter, the "progress ring" toggle, and distraction risk

**Observed:** in `follow_along`, `dwell.visual_cursor` toggles the yellow gaze cursor on/off as expected. Toggling `dwell.progress_ring` produced no visible change. Raw cursor jitter is distracting to children during trials (observed by the physician).

**Investigated:**
- `dwell.visual_cursor` (`configs/default.yaml`) → `TaskCanvas.show_cursor` (`src/ui/canvas.py`). Wired correctly — matches what was observed.
- `dwell.progress_ring` → `TaskCanvas.show_progress_ring`. Also wired correctly, **but** the ring (`_draw_progress_ring`) is only ever painted while `dwell_progress > 0`, i.e. only during an active dwell accumulation. If gaze never accumulated dwell progress during the test (see item 2), the ring would never have appeared regardless of the toggle — so "no visible change" doesn't necessarily mean the setting is broken.
- The cursor position painted every frame comes straight from the tracker's raw best-point-of-gaze (BPOGX/BPOGY, falling back to FPOGX/FPOGY in `gazepoint_client.py::rec_to_sample`). **No smoothing, averaging, or filtering is applied anywhere in the codebase** before that point is rendered. Raw point-of-gaze is inherently noisy on any video-based tracker, and pediatric gaze tends to be noisier than adult gaze — the pipeline currently passes 100% of that raw noise straight to the screen. This is a confirmed, real gap, not a device malfunction.

**Open question:** is jitter itself the nuisance, or is it mainly a problem because it interferes with selection (item 2)? Both point to the same root cause (unfiltered raw signal) but the answer affects where a future fix should focus.

## 2. Gaze on target doesn't "light up" the target

**Observed:** gaze landing on the follow_along target doesn't visibly register right away; feels unresponsive.

**Investigated:**
- The target's appearance does not change the instant gaze lands on it. The *only* on-target feedback is the dwell progress ring, which requires **800ms continuous on-target dwell** (`dwell.threshold_ms`) to complete.
- A **120ms hold-grace** window (`DwellConfig.hold_grace_ms` in `src/inputs/eye_input.py`, hardcoded, not in any YAML) tolerates brief drop-offs without resetting — but if the jittery raw gaze (item 1) drifts outside the target hitbox for longer than 120ms, dwell progress resets to zero and restarts.
- There is no "instant" visual acknowledgment of on-target gaze independent of the slow-filling ring.
- **This is very likely the same underlying issue as item 1, seen from a different angle:** jittery raw gaze pushes the pointer in and out of the hitbox faster than the 120ms grace tolerates, so dwell progress keeps resetting before it becomes visually obvious — which looks and feels exactly like "gaze on target, nothing happens."
- The hitbox itself already has generous slack (`dwell.jitter_tolerance_px = 40px` added to the target radius), so positional tolerance is not the bottleneck — the 120ms *temporal* tolerance is.

## 3. What each of the four tasks is for, and why three of them look alike

**Observed:** `follow_along` is distinguishable, but `click_static`, `click_grid`, and `scanning` look similar during testing.

**Investigated (implementation fact, stated for diagnosis only):**
- `TaskCanvas.paintEvent` (`src/ui/canvas.py`) only ever draws **one** target circle — the single currently-active target, plus the cursor, dwell ring, and hit particles. There is no rendering path for multiple simultaneous shapes.
- `click_grid.yaml` declares a 3×3 grid and a `highlight_color`, implying "show all 9 cells, highlight the active one." `scanning.yaml` declares `n_icons: 4` distractors and its own `highlight_color`, implying "show all icons, highlight the target." **Neither layout is actually drawn.** Both tasks currently render exactly like `click_static`: one circle appears at a new position each trial. The grid/icon-slot logic exists only in the Python target-*position* sampling (`click_grid.py`, `scanning.py`) and the YAML — never on screen.
- **This is the direct cause of the "they all look the same" observation.** Visually, all three are currently indistinguishable single-target click tasks; only the underlying position-sampling pattern differs (fixed grid cells vs. 8 random candidate positions vs. a row of slots), and none of that is visible to the child or observer.

**Clinical purpose of each task (external research):**

| Task | Mechanism | What it's designed to measure | Supporting source |
|---|---|---|---|
| `follow_moving` | Target moves along a path; child must continuously track and select it in a timed window | **Smooth pursuit** (continuous tracking), a distinct oculomotor system from fixation/saccades with faster onset latency (~90-150ms vs ~200-250ms for voluntary saccades) | Wikipedia/iMotions eye-movement physiology overview |
| `click_static` | One static target at a random position; fixate + dwell-select | **Single-target fixation (STF)** — ability to direct and hold gaze on one isolated static stimulus | Matches the "STF" task in a 2025 peer-reviewed study assessing gaze fixation/shift specifically in children with CP (PubMed 40217776, *J Clin Med* 2025) |
| `click_grid` | Explicitly modeled on "Compass" (per its own code docstring); 3×3 grid, one cell should light up | **Spatial/positional selection accuracy** among an array of candidate locations — closer to real AAC grid-interface use than raw oculomotor testing | Compass is the same software used in a published longitudinal study measuring gaze-based AT performance (time-on-task, accuracy) in children with CP (PMC4867850) |
| `scanning` | Several icons shown; one is cued as target among distractors | **Visual search / target-target fixation shift (TTFS)** — finding and shifting gaze to a designated item among competitors, distinct from static fixation | Matches "TTFS," the second task type in the same 2025 CP study above; matches the general OT distinction between "visual tracking" (single moving target) and "visual scanning" (searching among several) (napacenter.org) |

**Conclusion:** the four tasks are clinically well-differentiated *by design* (pursuit vs. static fixation vs. spatial accuracy vs. search/shift), but `click_grid` and `scanning` are not currently rendering the multi-item layouts that would make that distinction visible — and, arguably, clinically valid. Right now they behave as `click_static` with different position sampling, which is exactly what was observed.

**Implemented 2026-09-03:** `BaseTask.layout_slots` (new, `src/tasks/base_task.py`) exposes each multi-item task's candidate positions; `ClickGridTask`/`ScanningTask` populate it (`src/tasks/click_grid.py`, `src/tasks/scanning.py`). `TaskCanvas._draw_layout_slots` (new, `src/ui/canvas.py`) paints every slot as a dim outline with the active target drawn bright on top, wired through `app.py`. Visually confirmed via qt-mcp screenshot against `--replay tests/fixtures/gaze_replay.jsonl` (no real device) for both tasks — `click_grid` now shows its 3x3 grid, `scanning` its 4-icon row. Tests: `test_click_grid_exposes_layout_slots_for_gui`, `test_scanning_exposes_layout_slots_for_gui`, `test_click_static_has_no_layout_slots` in `tests/test_task_pipeline.py`.

## 4. Missing sound feedback: bug, or missing asset?

**Observed:** no sound when a trial completes.

**Investigated — confirmed: not a bug. The feature was never built.**
- No audio files exist anywhere in the repository (searched for `.wav`/`.mp3`/`.ogg` — none found).
- No audio-playback code exists anywhere in `src/` (searched for `QSound`, `QMediaPlayer`, `playsound`, `winsound` — no matches).
- `FeedbackBus` (`src/engine/feedback.py`) is the intended abstraction for feedback effects, but the GUI's concrete implementation (`GuiFeedback` in `src/app.py`) only implements `on_hit` → a particle burst on the canvas. `on_miss`, `on_progress`, and `on_target_shown` are all no-ops — no sound is triggered for any of them.
- **Every** task YAML (`click_static.yaml`, `click_grid.yaml`, `scanning.yaml`, `follow_moving.yaml`) declares `feedback.hit_sound: true` and `feedback.miss_sound: true` — but these keys are never read by any Python code. They are dead configuration, most likely a placeholder left over from the original design plan that was never wired up.
- **Answer:** audio feedback is a planned-but-unbuilt feature, not a regression. (Informational only, not a plan: PySide6 already ships `QSoundEffect`/`QMediaPlayer` for whenever this gets built, so no new dependency would be needed — only sound assets, which would need to be sourced/licensed.)

**Implemented 2026-09-03.** Discrete hit/miss cues only (no continuous background music — deliberately out of scope, see rationale below). Each theme (`configs/themes/space.yaml`, `configs/themes/forest.yaml`) already declared a `sounds.hit`/`sounds.miss` path pointing at files that didn't exist; those are now real assets, and `GuiFeedback` (`src/app.py`) now honors `feedback.hit_sound`/`feedback.miss_sound` from each task YAML (closing the exact dead-config gap this item diagnosed) by playing the matching theme cue via `QSoundEffect` on `on_hit`/`on_miss`, at a deliberately reduced volume (0.6) as a sensory-overstimulation safety margin.

- **Scope decision — discrete cues, not background music:** the user's initial framing of this task mentioned "background music," but continuous audio during active trials was explicitly ruled out (user decision, 2026-09-03) as a possible auditory distractor/confound for a visual-attention gaze assessment in a CP/CVI population — there was no clinical-literature basis in this SPEC for adding it, and it would have been new scope beyond the originally diagnosed gap. Scope stayed to the two cues already declared in config.
- **Asset generation:** 4 short (1.2s) WAV cues generated via the user's own `mcp-audio-openrouter` MCP tool (`generate_music`, `google/lyria-3-clip-preview`, OpenRouter) — `space_hit`/`space_miss` (used by `click_grid`/`follow_moving`) and `forest_hit`/`forest_miss` (used by `click_static`/`scanning`). Prompts were designed for the target population specifically, not generically: short, soft, non-startling timbres (bell/chime/xylophone, no drums/bass), a warm ascending two-note phrase for "hit," and a neutral (never punitive/buzzer-like) descending two-note tone for "miss" — an assessment tool's miss cue must not risk discouraging engagement or biasing the child's behavior, which would taint the very accuracy/reaction-time data being collected. User approved the exact prompts before generation.
- **Length-mismatch workaround:** `generate_music`'s shortest preset is a ~30s "clip" (no sub-30s option exists) and the model did not reliably honor a "fade to silence quickly" instruction — all 4 generations played continuously for the full clip. Each was trimmed locally to a clean, short cue via `ffmpeg` (bundled through the pip-installable `imageio-ffmpeg`, run in an ephemeral `uv run --with imageio-ffmpeg` environment — not an app dependency) using a `silencedetect`-then-hard-cap approach, saved as `configs/assets/sounds/{space,forest}_{hit,miss}.wav`, 1.2s each. Raw 30s originals remain in the audio tool's own (gitignored) `output/` dir for reference/re-trimming without paying for regeneration.
- **Diagnosed but NOT resolved in this session — `QSoundEffect` reports `Status.Error` for every WAV tried, in this session's environment specifically.** Live qt-mcp testing surfaced a Qt warning ("playback of this format is not supported on the selected audio device") for both cues on every launch. One real candidate cause was ruled out along the way: ffmpeg's WAV export inserts a `LIST/INFO` metadata chunk between the `fmt ` and `data` chunks, which some minimal WAV parsers reject — final assets are re-exported without it (`-map_metadata -1 -fflags +bitexact`, canonical 16-bit PCM stereo 48kHz header verified byte-for-byte), but the warning persisted unchanged afterward, so it was not the (sole) cause. Conclusively isolated with a control test: a completely stock Windows system sound (`C:\Windows\Media\chimes.wav`), loaded via a minimal standalone `QSoundEffect` script, fails identically (`Status.Error`, `isLoaded: False`) — proving this is an audio-output-device limitation of the automated session this work ran in, not a defect in the generated files or the app's wiring code.
- **Verification caveat — could not be audibly confirmed by the implementing session, for the reason above.** The generated files are independently confirmed structurally valid: Python's `wave` module reads all 4 cleanly (correct channel count/sample width/rate/duration), and `System.Media.SoundPlayer.PlaySync()` — a separate, non-Qt Windows audio API — played `space_hit.wav` successfully. The app itself never crashes regardless of the audio-device failure (`QSoundEffect.play()` on an errored source is a safe no-op) — verified across three live qt-mcp GUI launches with no exception. **The user should listen to the 4 files themselves** (`configs/assets/sounds/*.wav`) on a machine with a working, bound audio output device and confirm both that they play at all and that they sound as intended, before considering this item fully done; regeneration/re-prompting is one MCP tool call away if not.
- **Tests:** `tests/test_theme_sounds.py` (new) — asserts each theme declares hit/miss sounds and that the files exist and are short (≤2s), valid 16-bit PCM WAV. Kept Qt-free, matching this project's existing convention of not unit-testing PySide6 GUI code directly (verified live via qt-mcp instead, as with item 3).

## 5. Are target speed and inter-trial pacing configurable?

**Observed:** wants to know if the follow_along circle can move slower, and if there's more pause between circles in the other tasks.

**Investigated — yes, both already exist as config, just not surfaced/documented for a non-engineer:**
- **follow_along movement speed:** `motion.speed_frac_per_s` in `configs/tasks/follow_moving.yaml`, currently `0.20` (fraction of screen width per second the target moves). Lower value = slower motion. A related setting, `motion.select_window_ms` (currently 2500ms), controls how long the moving target stays selectable/highlighted.
- **Inter-trial pacing, all four tasks:** `inter_trial_interval_ms` in each task's YAML controls the pause between one trial ending and the next target appearing — this is the "time between circles" being asked about. Current values: `click_static` 800ms, `click_grid` 800ms, `scanning` 900ms, `follow_moving` 1000ms.
- There is no separate "appear" animation — the next target simply appears the instant the inter-trial interval elapses; the pause itself is the only adjustable "slowness" between targets.
- Each task also has its own independently configurable `timeout_ms` (how long a trial waits before giving up), in case that overlaps with what "slower" was meant to address.

## 6. Meaning of recorded/analysis data fields, and what's clinically relevant for CP

**Observed:** physician asked what the saved data fields mean; user couldn't answer. Also: what GP3HD data is actually relevant for assessing Cerebral Palsy?

**Investigated — fields currently written to disk per session (`sessions/<session_id>/`):**

`trials.csv` — one row per completed trial:

| Field | Meaning |
|---|---|
| `trial_id`, `task_id` | trial index, task name |
| `target_x`, `target_y` | normalized (0-1) target position |
| `target_radius_px` | target hitbox radius, pixels |
| `t_target_shown_ns` | timestamp the target appeared |
| `t_first_gaze_on_target_ns` | timestamp gaze *first* entered the target hitbox (first-fixation time) |
| `t_click_ns` | timestamp of the successful dwell-selection |
| `t_end_ns` | timestamp the trial ended (hit or timeout) |
| `is_hit` / `is_timeout` | outcome flags |
| `attempts` | number of selection attempts in the trial (off-target attempts count too) |
| `reaction_time_ms` | `t_click_ns − t_target_shown_ns` |
| `time_to_first_fixation_ms` | `t_first_gaze_on_target_ns − t_target_shown_ns` |

`gaze_stream.csv` — raw per-sample gaze log (if `recording.save_gaze_stream` is on): `t_ns`, `x`/`y` (normalized point of gaze), `valid`, `fixation_id`, `fix_duration_s`, `pupil_left`/`pupil_right` (mm).

`metadata.json` — subject/session IDs, calibration point count, mean calibration error in px, input mode, task list.

`events.jsonl` — the raw event log (`TARGET_SHOWN`, `MISS_CLICK`, `HIT`, `TIMEOUT`, `LATENCY_SAMPLE`, ...) that the above are derived from.

**What `analysis/analyze_session.py` currently computes:** hit rate, timeout count, mean reaction time, a reaction-time histogram, and a 2D gaze heatmap. Nothing pupil- or fixation-specific is summarized today, even though `pupil_left`/`pupil_right`/`fixation_id`/`fix_duration_s` are already recorded in the raw stream.

**What's clinically relevant from a GP3HD-class tracker for CP assessment (external research):**

- **Fixation & saccade latency, frequency, and "off-screen" proportion.** A 2025 study (*Ophthalmology Science*/ScienceDirect) found six such features together reached AUC ≥0.90 distinguishing children with cerebral/cortical visual impairment (common in CP) from age-matched controls, and tracked them longitudinally as an objective outcome measure. This tool already records the raw ingredients for these (`fixation_id`, `fix_duration_s`, per-trial timestamps) but doesn't yet aggregate them into session-level features.
- **Time-on-task and selection accuracy.** The metrics used in a published longitudinal study of gaze-based AT (using the same "Compass" software `click_grid` is explicitly modeled on, per its own code docstring) that tracked real functional improvement in children with CP over months of use (PMC4867850). This tool's `reaction_time_ms`/`is_hit`/`attempts` already map onto this directly.
- **Single-target fixation vs. target-target fixation shift.** A 2025 study (PubMed 40217776) assessing exactly these two skills in children with CP found meaningful child-to-child variability between them — reinforcing why visually and clinically distinguishing `click_static` (fixation) from `scanning`/`click_grid` (shift/search) matters (ties back to item 3's finding that they're currently indistinguishable).
- **Pupil diameter.** Already captured (`LPMM`/`RPMM` via the GP3HD) but never summarized. In the wider literature this is used mainly as a cognitive-load/attention/arousal signal rather than a CP-specific oculomotor marker — likely lower priority than the fixation/saccade features above, unless the clinical goal explicitly includes attention/engagement tracking.
- **Calibration accuracy per subject.** Already recorded (`calibration_error_px`) and clinically meaningful in its own right, not just as tooling QA: the 2025 CP fixation study reported 6 of 39 children were unable to calibrate to the required accuracy at all — calibration success/quality is itself a data point about a child's oculomotor control.

**Partially implemented 2026-09-03:** `src/data/exporter.py` gained `load_gaze_rows`, `compute_fixation_saccade_metrics` (session-level fixation count/rate/duration mean-median-max, saccade count/rate, valid-gaze ratio, mean pupil L/R mm — all aggregated from the already-recorded `gaze_stream.csv`, no new tracker data needed), and `compute_trial_fixation_counts` (distinct fixation count per trial window — the single-target-fixation vs. target-target-fixation-shift signal called out above). Wired into `analysis/analyze_session.py`, which now also writes a `session_metrics.json` into the session directory. Ran successfully against the real recorded session at `dev/sessions/saved_session_data` (a `scanning` replay: 114 fixations, 0.30s mean duration, 3.34mm mean pupil). Tests added to `tests/test_recorder.py`. **Not yet done:** turning this into a CVI-style session report/dashboard, or extending it to the AUC-relevant off-screen-proportion / saccade-latency features beyond what's listed here — this is the raw metrics aggregation layer only, open item 4 below is still open.

## 7. Calibration re-runs on every task launch, even for the same child

**Observed:** not one of the original six physician feedback items — surfaced 2026-09-03 while drafting a report summary, from the user's own question: "does the same subject need to calibrate again for a different task?"

**Investigated:**
- `src/main.py`'s CLI only accepts a single `--task` per invocation (`argparse` `choices=sorted(TASK_REGISTRY)`), so running all four tasks for one child means launching the app four separate times as four separate processes.
- `AssessmentApp.__init__` (`src/app.py`) runs `Calibration(self.client, ...).run()` fresh on every launch, gated only by `calibration.enabled` in config — there is no session-level state that persists across process launches, so a fresh calibration happens each time regardless of whether the same child sat through one moments earlier.
- **Not a bug** — this is simply how the app is structured today (one process = one task = one calibration). No code currently supports "calibrate once, then run task A, then task B without recalibrating."

**Why this likely matters:** eye-tracker calibration accuracy is generally expected to stay valid as long as head position/distance from the tracker hasn't changed meaningfully — re-running full calibration between tasks in the same sitting adds repeated setup time and burden for children who may fatigue or lose patience easily, without a clear accuracy benefit if the child hasn't moved.
